# Архитектура Apex CRM

## Назначение

Apex CRM — PWA и Telegram-бот для работы автосервиса. Система хранит клиентов,
автомобили, записи, заказ-наряды, диагностику и финансовые показатели. ИИ через
OpenRouter используется для разбора команд, документов автомобиля и чеков.

## Текущие компоненты

| Компонент | Технологии | Расположение | Ответственность |
| --- | --- | --- | --- |
| PWA | React, TypeScript, Vite | `frontend/` | Интерфейс пользователя и обращение к `/api` |
| HTTP API | FastAPI | `pwa.py` | Авторизация, RBAC, валидация и HTTP endpoints |
| Telegram-бот | aiogram | `bot.py` | Диалоги и команды CRM через Telegram |
| Домен и данные | Python, SQLite/PostgreSQL | `database.py`, `postgres_backend.py` | Транзакции и хранение данных |
| ИИ-интеграция | OpenRouter, aiohttp | `openrouter.py` | Структурированные ответы моделей и их валидация |
| Поставщики | aiohttp, XML/JSON | `supplier_catalog.py` | Поиск и импорт запчастей |
| Инфраструктура | Caddy, systemd, Docker Compose | `deployment/`, `docker-compose.yml` | HTTPS, процессы и PostgreSQL |

Поток веб-запроса:

`React PWA -> Caddy/HTTPS -> FastAPI -> Database -> SQLite или PostgreSQL`

Внешние вызовы выполняются только backend-компонентами. API-ключи OpenRouter и
поставщиков не должны передаваться в браузер или попадать в Git.

## ИИ-контур и границы доверия

Ввод пользователя, изображения, ответы ИИ и ответы поставщиков считаются
недоверенными данными. JSON Schema провайдера не заменяет серверную проверку.

- Backend проверяет типы, длину строк, диапазоны сумм и количество элементов.
- Итог распознанного чека пересчитывается по проверенным строкам.
- Ответ ИИ не должен исполняться через `eval`, shell или динамический SQL.
- Изменяющая данные команда проходит обычные проверки прав и бизнес-правила.
- XML поставщика разбирается безопасным парсером, ответы ограничены по размеру.
- Секреты находятся только в `.env` сервера; в логи отправляются только безопасные
  метаданные использования модели.

## Модульность и принципы разработки

Frontend уже разделён на `app`, `components`, `features`, `lib` и `pages`.
Компоненты представления не должны самостоятельно рассчитывать финансовые итоги:
общая математика размещается в тестируемых функциях `lib`.

Backend отделён от frontend, но пока является модульным монолитом. Файлы `bot.py`,
`database.py` и `pwa.py` слишком велики и объединяют несколько ответственностей.
Целевая структура без обязательного перехода к микросервисам:

```text
backend/
  api/             # FastAPI routers, middleware, HTTP schemas
  application/     # сценарии использования и транзакционные границы
  domain/          # сущности и бизнес-правила без FastAPI/SQL/aiogram
  infrastructure/  # БД, OpenRouter, поставщики, файлы
  bot/             # Telegram handlers и presentation layer
frontend/
  src/app/
  src/features/
  src/components/
  src/lib/
  src/pages/
deployment/
tests/
```

Практическое применение SOLID:

- одна причина изменения у router/service/repository;
- бизнес-логика зависит от интерфейсов репозиториев, а не от FastAPI или SQL;
- внешние интеграции реализуют небольшие адаптеры;
- схемы HTTP не используются как доменные сущности;
- зависимости передаются явно, глобальное состояние постепенно исключается;
- сначала тестируется публичное поведение, затем детали реализации.

Микросервисы сейчас не требуются: бот и PWA используют одну транзакционную модель.
Их преждевременное разделение добавит распределённые транзакции и усложнит деплой.

## Безопасность

- Access JWT действует 10 минут, передаётся как `Authorization: Bearer` и хранится
  только в памяти PWA. Проверяются подпись HS256, `alg`, `typ`, `iss`, `aud`, `sub`,
  `org`, `iat`, `nbf`, `exp`, `jti` и идентификатор семейства сессии.
- Refresh token действует 30 дней и хранится в `HttpOnly; Secure; SameSite=Strict`
  cookie. В БД сохраняется только HMAC-хеш. При обновлении token ротируется;
  повторное использование старого token отзывает всё семейство.
- Logout, смена пароля и блокировка учётной записи делают активную сессию
  недействительной на сервере, включая уже выданный access JWT.
- Все CRM API, кроме маршрутов входа/обновления/выхода, закрываются централизованно.
- Права проверяются сервером; скрытие элементов интерфейса не считается защитой.
- Cookie или refresh-токены: `HttpOnly`, `Secure`, `SameSite=Strict`.
- Пароли хешируются стойким password KDF; секреты регулярно ротируются.
- SQL использует параметры, загружаемые файлы проверяются по размеру и сигнатуре.
- Перед релизом выполняются unit/integration tests, dependency audit и SAST.

## Тестирование и критерии релиза

Backend:

```bash
python -m unittest discover -v
pip-audit -r requirements.txt
bandit -r . -x .venv,frontend -lll
```

Frontend:

```bash
pnpm --dir frontend install --frozen-lockfile
pnpm --dir frontend test
pnpm --dir frontend typecheck
pnpm --dir frontend lint
pnpm --dir frontend build
pnpm --dir frontend audit --prod --audit-level moderate
```

Релиз запрещён при падении тестов, typecheck, lint, сборки или при обнаружении
уязвимости высокой критичности.

## CI/CD

CI/CD реализован через GitHub Actions. Production работает через Caddy и две
systemd-службы из `deployment/`. Инструкция по секретам, правам сервера и первому
запуску находится в `docs/DEPLOYMENT.md`.

Целевой pipeline для GitHub:

1. Pull request: backend tests, frontend tests/typecheck/lint/build, dependency audit.
2. Merge в защищённую `master`: повторная проверка и сборка неизменяемого артефакта.
3. Deployment environment с ручным approval: резервная копия БД, доставка артефакта,
   установка зависимостей, миграции, атомарное переключение релиза.
4. Перезапуск `apex-crm-pwa` и `apex-crm-bot`, затем `/health` и smoke tests.
5. При ошибке health check — автоматический откат на предыдущий артефакт.

Для включения CD нужны GitHub Environment и секреты `DEPLOY_HOST`, `DEPLOY_USER`,
`DEPLOY_SSH_KEY`, `DEPLOY_HOST_KEY`. `.env`, БД, backups и uploads не должны входить
в артефакт или передаваться через GitHub Actions. Серверный SSH-ключ рекомендуется
ограничить отдельной deployment-командой и минимальными правами `sudo` только на
необходимые systemd-службы.

## Архитектурные решения

- Сохранять модульный монолит до появления независимых команд, масштабирования или
  требований к отдельной доступности компонентов.
- PostgreSQL использовать в production; SQLite оставлять для локальной разработки
  и тестов.
- Рефакторинг начинать с выделения FastAPI routers и repository/service-слоя, не
  совмещая его с функциональными изменениями.
- Изменения схемы БД переводить на версионируемые миграции до включения CD.
